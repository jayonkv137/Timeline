# COTRACE Pipeline — Technical Specification
### Goal Hierarchy, Requirement, & Influence Extraction Layer (Steps 1a · 1b · 1c · 2 · 3)

**Document status:** Living reference, v3. Grounded in COTRACE (Kim et al., *Measuring AI
Contributions to Goal Shaping*, Appendix B). v3 adds Step 3, and enforces a strict rule:
**prompts are clean, production-ready text with zero inline annotation.** Every change we've
made to a paper's original prompt is documented in a table immediately AFTER that prompt —
never inside it. v3 also adds §9, a full cross-step iteration mechanism, previously undocumented.

**Scope:** Every prompt in the goal/requirement/influence extraction layer, as a complete
request/response contract, with exact production-ready prompt text. Does not cover Stage 4
(Quantification), documented separately.

---

## 1. How to read this document

Every step follows the same structure:

1. **Overview** — purpose, calling cadence, place in the pipeline.
2. **PROMPT** — the exact text to send the model. **Clean. No brackets, no markup, nothing
   that isn't meant for the model to read.**
3. **Changes from the paper's original prompt** — a table, placed immediately after the
   prompt, documenting every addition/edit and why. This is where all commentary lives.
4. **REQUEST** — every input placeholder: provenance, exact source, first-call behavior.
5. **RESPONSE** — every output field: type, values, *nature*.
6. **Transformation** — what happens to the response before it becomes another input.

### 1.1 Provenance (REQUEST / input placeholders)

| Code | Meaning |
|---|---|
| **RAW** | Comes directly from the real chat transcript — not derived from any model output. |
| **ACCUMULATE** | The full running total of a prior step's output across every call so far. |
| **FILTER** | A subset of a prior step's output, selected by a lookup/join rule. |
| **SELF-REFERENCE** | This same step's own output from a previous call, fed straight back in. |
| **ECHO** | A single already-known value, restated so the model has it in view. |
| **DERIVED** | Computed from prior outputs by a fixed rule, not asked for directly anywhere. |

### 1.2 Nature (RESPONSE / output fields)

| Code | Meaning |
|---|---|
| **VERBATIM** | Copied character-for-character from the dialogue. |
| **ASSIGNED ID** | A fresh label invented purely as a unique key; meaningless alone. |
| **DERIVED ID** | An identifier that should be computed by formatting/code, not model judgment. |
| **CLASSIFIED** | Picked from a small, defined, closed set of options. |
| **SYNTHESIZED** | Free text generated by the model — a paraphrase or summary, not a quote. |
| **STRUCTURAL JUDGMENT** | The model deciding a relationship between two identified things. |
| **UNVALIDATED SELF-REPORT** | The model's own uncalibrated certainty; no rubric, no consumer. |

**Only ONE input in the entire pipeline is RAW** (Step 1a's `{dialogue block}`). Everything
else is manufactured entirely from a prior model output.

### 1.3 Placeholder naming — deterministic, no reuse across steps

| Name | Used in | Scope |
|---|---|---|
| `{all actions block}` | Step 1b only | Every action, whole dialogue, ACCUMULATE |
| `{outcome actions block}` | Step 2 only | Actions bound to one outcome, FILTER |
| `{preceding block}` / `{subsequent block}` | Step 3 only | Actions relative to one requirement's origin turn |
| `{dialogue turns}` | Step E1 only | Raw turn text for one outcome's turns, FILTER over RAW |
| `{deliverable text}` / `{requirements}` / `{open slots}` | Step E2 only | E1's output piped in / one outcome's active requirements / one outcome's still-open slots |

No placeholder name is ever shared between two steps with different scope. Permanent policy.

## 3. STEP 1a — Action Extraction

**Purpose:** segment raw dialogue into atomic, speaker-tagged, role-labeled actions.
**Cadence:** once per block. **B = 1 pair** (§11.1).

### 3.1 PROMPT

```
You are analyzing **one block of a longer dialogue** to extract actions.

**ACTION** = An atomic communicative act a speaker **directly performed** in a turn.
- Atomic action = minimal unit of action the speaker directly performed. - e.g.
"User asks to find a paper about HCI in NLP conferences" → split into "User asks
to find a paper about HCI", "User asks to find a paper in NLP conferences".
- Include evidence quote from the utterance.

**Possible action types** (generate new types if needed):
Accept, Acknowledge, Address, Allow, Analyze, Apologize, Ask, Challenge, Clarify,
Classify, Compare, Complain, Confirm, Connect, Constrain, Critique, Decide, Define,
Delegate, Describe, Draft, Emphasize, Evaluate, Explain, Feedback, Formalize, Frame,
Greet, Hypothesize, Implement, Include, Infer, Instruct, Invite, Justify, List,
Modify, Observe, Plan, Provide, Qualify, Recommend, Refuse, Report, Request, State,
Suggest, Summarize, Warn

**Role:** **SHAPER | EXECUTOR | OTHER**
* **SHAPER:** Creates/shapes/revises the goal/requirement by proposing new ideas,
new tasks, constraints, alternatives, or directions.
* **EXECUTOR:** Executes/achieves the desired outcome/goal/requirement (e.g.,
drafting text, providing requested information, coding, searching, implementing).
* **OTHER:** Neither SHAPER nor EXECUTOR.

**Turn ID format:** each turn is labeled **U(x,y)** or **A(x,y)**, where **U**=user
turn, **A**=AI turn, **x**=the pair number this turn belongs to (the 1st user+AI
exchange is pair 1, the 2nd is pair 2, etc.), and **y**=the action's position
within that turn (1, 2, 3… in the order it was extracted). e.g. the user's 2nd
atomic action in pair 1 is "U(1,2)"; the AI's 1st atomic action in pair 3 is
"A(3,1)". Use this format for every turn id below — do not use plain integers.

=== DIALOGUE BLOCK START ===
{dialogue block}
=== DIALOGUE BLOCK END ===

Now, extract ALL actions from EVERY turn. Return JSON only, pretty-printed with
2-space indentation and each key on its own line (not compact/single-line
objects):
{ "actions": [ { "turn id": "<U(x,y) or A(x,y)>", "action type": "<action type>",
"action text": "<brief description in third person>", "role":
"<SHAPER|EXECUTOR|OTHER>", "evidence quote": "<quote from utterance>" } ]
}
Respond with ONLY the JSON object. No additional text.
```

### 3.2 Changes from the paper's original prompt

| Addition | Paper had | We changed to |
|---|---|---|
| "Turn ID format" paragraph | Plain `<turn number>` integer, no format defined | `U(x,y)`/`A(x,y)` labeled format, fully specified with worked examples |
| "pretty-printed with 2-space indentation..." clause | No output-formatting instruction | Light nudge toward readable output. **The real guarantee is code-side re-serialization (§11.5) — this clause helps but is not the sole safeguard.** |

### 3.3 REQUEST

| Placeholder | Provenance | Exact source | Empty on first call? |
|---|---|---|---|
| `{dialogue block}` | **RAW** | Real `U`/`A` text for this pair, formatted with an explicit pair-number label so the model reads `x`, never infers it. | No. |

### 3.4 RESPONSE

| Field | Type | Possible values | Nature | Role |
|---|---|---|---|---|
| `turn id` | string | `U(x,y)` \| `A(x,y)` | `x`=**DERIVED ID**, `y`=**ASSIGNED ID**. | Primary key for every action, referenced by every later schema. |
| `action type` | string, open vocabulary | ~50 listed types or a new one. | **CLASSIFIED** (open-set). | Human-readable categorization. |
| `action text` | string, free text | Third-person description. | **SYNTHESIZED**. | Human-readable paraphrase. |
| `role` | enum | `SHAPER` \| `EXECUTOR` \| `OTHER` | **CLASSIFIED**, strictly. | **Most load-bearing field in the pipeline.** |
| `evidence quote` | string | Must literally appear in the source. | **VERBATIM**. | The audit trail. |

### 3.5 Transformation → next step
`actions[]` **appended** to STATE's running list. Feeds Step 1b's `{all actions block}`.

## 4. STEP 1b — Outcome Extraction

**Purpose:** identify the outcome tree and map every action to exactly one outcome.
**Cadence:** once per pair, right after 1a.

### 4.1 PROMPT

```
Step 1b: Outcome Extraction

You are given ALL actions extracted from a complete dialogue. Your task:
(1) Identify **outcomes** (purpose-linked desired deliverables)
(2) Assign every action to exactly one outcome
(3) Maintain the dialogue summary: if the collaboration's core purpose is
unchanged since the prior summary, return it unchanged; if new actions
materially extend or shift that purpose, revise the summary to reflect the
fuller picture. Keep it to 1-2 sentences regardless of which case applies.

Every collaboration has a **purpose**. **Outcomes are purpose-linked desired
deliverables** --- concrete outputs that participants are actually working toward.
- **Outcomes = purpose-linked desired deliverables:** Deliverables are not limited
to text or documents --- they can be a **decision**, **advice**, **plan**,
**clarification**, or any other concrete result. Do **not** include things only
mentioned without being adopted as a goal. - **Requested or agreed outputs:** Any
concrete output a participant **explicitly requests** or participants **agree to
produce** is a deliverable. - **Primary output:** The main thing the dialogue aims
to produce must appear as an outcome. Sub-deliverables are children. - **Phrasing:**
e.g. "decision for X", "advice for X", "draft for X", "plan for X". - **Hierarchy:**
**parent** = abstract/general, **child** = specific/concrete. Use parent outcome id
/ child outcome ids. - **Granularity:** Prefer consolidated, task-level outcomes.
Example: "Workshop plan (date, venue, agenda)" NOT separate "Decide date", "Decide
time", etc. - **No duplicates.** Each distinct deliverable exactly once.

=== DIALOGUE CONTEXT (prior dialogue summary; empty on first call) ===
{dialogue summary}
=== ALL ACTIONS (every action accumulated across the whole dialogue so far) ===
{all actions block}

Return JSON only:
{ "dialogue summary": "<collaboration purpose, 1-2 sentences>", "outcomes": [
{ "outcome id": "outcome 1", "outcome": "<purpose-linked desired deliverable
description>", "turn id": "<U(x,y) or A(x,y) of the action where this outcome
first appears>", "parent outcome id": null, "child outcome ids": [], "related
outcome ids": [], "confidence": <float 0.0--1.0> } ], "action to outcome": {
"<action id>": "<outcome id>" } }
IMPORTANT: action to outcome must map EVERY action id to an outcome id. No action
left unassigned.
Respond with ONLY the JSON object. No additional text.
```

### 4.2 Changes from the paper's original prompt

| Addition | Paper had | We changed to |
|---|---|---|
| Task (3), dialogue-summary maintenance rule | `dialogue_summary` requested only in the output schema — never tasked, no process defined anywhere in the paper (confirmed by direct source check) | Explicit numbered task with a stability-by-default update rule (§4.6) |
| Section labels ("prior dialogue summary; empty on first call", "accumulated across the whole dialogue so far") | Bare `=== DIALOGUE CONTEXT ===` / `=== ALL ACTIONS ===` | Clarifying parentheticals |
| `{actions block}` → `{all actions block}` | Same placeholder name reused ambiguously in Step 2 too | Renamed to disambiguate whole-dialogue scope (§1.3) |
| `turn id` inside `outcomes` | Plain integer | `U(x,y)`/`A(x,y)` string, consistent with Step 1a |

### 4.3 REQUEST

| Placeholder | Provenance | Exact source | Empty on first call? |
|---|---|---|---|
| `{dialogue summary}` | **SELF-REFERENCE** | This step's own prior output. | **Yes** — nothing to reference on the very first call. |
| `{all actions block}` | **ACCUMULATE** | Every action from every Step 1a call so far. | No. |

### 4.4 RESPONSE

| Field | Type | Possible values | Nature | Role |
|---|---|---|---|---|
| `dialogue summary` | string | 1–2 sentences. | **SYNTHESIZED**, per task (3)'s explicit process. Carried forward. | Compressed context anchor. |
| `outcome id` | string | `"outcome 1"`, … unique across the whole dialogue. | **ASSIGNED ID**. | Primary key. |
| `outcome` | string | Consolidated deliverable description. | **SYNTHESIZED**, rule-constrained. | The literal text your goal panel displays. |
| `turn id` | string | `U(x,y)`/`A(x,y)` of introducing action. | **STRUCTURAL JUDGMENT** — use the first SHAPER action if the outcome spans several actions in one turn. | Anchors the outcome in time. |
| `parent outcome id` | string \| `null` | `outcome_id` or `null` for root. | **STRUCTURAL JUDGMENT**. | Defines the goal tree's shape. |
| `child outcome ids` | array | Zero or more `outcome_id`s. | **STRUCTURAL JUDGMENT**, must agree bidirectionally with parent. | Feeds R-GROUP. |
| `related outcome ids` | array | Zero or more `outcome_id`s. | **STRUCTURAL JUDGMENT**. | Feeds R-TREE back-references. |
| `confidence` | float | `0.0`–`1.0`. | **UNVALIDATED SELF-REPORT** — no rubric, never consumed downstream. | **Recommendation: ignore.** |
| `action to outcome` | dict | Every action id → an `outcome_id`, exhaustive. | **STRUCTURAL JUDGMENT**, hard completeness rule. | Join table for Step 2's FILTER. |

### 4.5 Transformation → next step
`outcomes[]` stored in STATE. `action_to_outcome` becomes Step 2's lookup table. `dialogue_summary` loops back as SELF-REFERENCE.

### 4.6 Why task (3) exists — the gap it closes
`dialogue_summary` was found, on direct check of Appendix B.1.1/B.1.2/B.2, to appear nowhere
in the paper's task list, definitions, or pipeline overview — only in the input placeholder
and output schema. Unlike `confidence` (truly unused downstream), `dialogue_summary` **is**
structurally consumed (SELF-REFERENCE into every later call), so an undefined process for it
is a real gap, not a cosmetic one. The fix: an explicit numbered task with a stability rule —
keep the summary unchanged unless the collaboration's purpose has materially shifted. This
mirrors the append-only stability principle used elsewhere in this pipeline.

### 4.7 Known risk, unresolved
No explicit `{prior outcomes}` input exists (unlike Step 2). Step 1b re-derives the whole
outcome tree from the full action list every call, trusting consistent `outcome_id` reuse.
Not yet resolved — open decision.

## 5. STEP 1c — Intention Extraction

**Purpose:** group outcomes into higher-level "why" categories, consumed only by R-SIDE.
**Cadence:** once per pair, right after 1b.

### 5.1 PROMPT

```
Step 1c: Intention Extraction

You are given a list of outcomes from a dialogue.

=== OUTCOMES ===
{outcomes list}

(1) Identify distinct **intentions** (high-level goals or purposes) that these
outcomes serve. (2) Assign each outcome to exactly one intention.

Output JSON only:
{ "intentions": [ {"intention id": "I1", "intention": "short label"},
{"intention id": "I2", "intention": "another label"} ], "outcome to intention":
[{"outcome id": "outcome 1", "intention id": "I1"}, ...] }
- Every outcome id appears exactly once in outcome to intention. Use intention id
from the intentions list.
```

### 5.2 Changes from the paper's original prompt

| Addition | Paper had | We changed to |
|---|---|---|
| `=== OUTCOMES === {outcomes list}` block | No explicit placeholder marked — only described in prose | Explicit placeholder added, matching the style of every other step |

### 5.3 REQUEST

| Placeholder | Provenance | Exact source | Empty on first call? |
|---|---|---|---|
| `{outcomes list}` | **ACCUMULATE** | Full `outcomes` list (id + description) from the latest Step 1b response. | No. |

### 5.4 RESPONSE

| Field | Type | Possible values | Nature | Role |
|---|---|---|---|---|
| `intention id` | string | `"I1"`, … own namespace. | **ASSIGNED ID**. | Primary key. |
| `intention` | string | Short label. | **SYNTHESIZED**. | Human-readable "why". |
| `outcome to intention` | array of pairs | Every `outcome_id` exactly once. | **STRUCTURAL JUDGMENT**, hard completeness+uniqueness. | Sole consumer: R-SIDE. |

### 5.5 Transformation → next step
`outcome_to_intention` stored, read only by R-SIDE. **Never reaches Step 2 or 3.**

## 6. STEP 2 — Requirement Extraction (+ Open-Slot Extension)

**Purpose:** for one outcome, extract binding success conditions. Content that fails
Necessity due to hedging/deferral is tracked as an open slot instead of being lost or
force-extracted.
**Cadence:** once per outcome **touched this pair** — a bounded fan-out (§9).

### 6.1 PROMPT

```
Step 2: Requirement Extraction

You are given ONE outcome and the actions bound to it. Extract **requirements**
(binding success conditions) for this outcome only.

=== OUTCOME ===
{outcome id}: {outcome description}
=== ACTIONS FOR THIS OUTCOME ===
{outcome actions block}
=== PRIOR REQUIREMENTS FOR THIS OUTCOME (if any; empty on first extraction) ===
{prior requirements block}
=== PRIOR OPEN SLOTS FOR THIS OUTCOME (if any; empty on first extraction) ===
{prior open slots block}

**REQUIREMENT** = An atomic, externally verifiable SUCCESS CONDITION for an outcome.
- Binary testable (pass/fail). - Must be explicitly stated or adopted as binding in
the dialogue.

**NOT a requirement:** content itself, advice, implementation methods, internal
reasoning, example outputs, one-off decisions.

Extract ONLY if ALL pass:
1) NECESSITY --- framed as mandatory (must/need/required/cannot, numeric
constraints, explicit include/exclude)
2) GROUNDING --- directly stated, no inference
3) REPLACEABILITY --- cannot be swapped without violating success
4) BINARY TESTABILITY --- reviewer can judge pass/fail

If an action raises a substantive idea, constraint, or decision point but FAILS
gate (1) NECESSITY specifically because of hedge or uncertainty language — this
includes option-uncertainty ("maybe", "could", "might", "may", "would possibly",
"perhaps", "mix / pick later"), epistemic hedges ("I think", "it seems", "I
believe", "it appears" — used to qualify the CONTENT of the claim, not as a
conversational filler elsewhere in the sentence), or approximation language
("about", "some", "most", "somewhat", "probably", "likely") — OR because the
action commits to determining something later rather than specifying it now
("I'll recommend based on your answer", "I'll decide after", "I'll verify before
committing") — do NOT discard it. Use the open_slot operation (see below) instead
of create. This applies only to Necessity failures caused by hedging, uncertainty,
or deferred content; failures of gates 2-4, content that is not substantive at all
(small talk, pure acknowledgment, restating something already said), or content
where a hedge word appears only as filler alongside an otherwise clearly mandatory
statement (e.g. "I think this must include X" — still a requirement, the hedge
qualifies the speaker's tone, not the requirement's content), are still handled
normally (dropped or extracted as create, respectively).

Operations:
- **create**: New requirement. Check PRIOR REQUIREMENTS above for revise BEFORE
create. - **revise**: Modify existing requirement (contradicts/tightens/
relaxes/replaces). Use EXACT existing req id (from PRIOR REQUIREMENTS) in related
to (within this outcome). - **delete**: Explicitly cancels a previously binding
condition. - **open_slot**: A hedged, uncertain, or deferred-content idea that
fails Necessity but is substantive enough to track — neither a binding requirement
nor nothing. Check PRIOR OPEN SLOTS above for resolve BEFORE open_slot: if this
action firmly answers/resolves a prior open slot, emit op="resolve" instead,
turning that slot into a new create with related to pointing at the resolved slot
id. Assign origin: "user" if the hedge came from the user's action, "AI" if from
the AI's action. A slot that has appeared in PRIOR OPEN SLOTS for 3 or more
consecutive pairs without being resolved should be marked op="abandon" — it is no
longer carried forward.

Edge cases:
- Advice itself is NOT a requirement. Only constraints ON the advice. - "Try to /
ideally / could / maybe" → not binding → not a requirement → check if substantive
enough for open_slot (see above); if not even substantive, drop entirely with no op.

Return JSON only (bound outcome id must be "{outcome id}"):
{ "requirement ops": [ { "op": "create", "req id": "req 1", "bound outcome id":
"{outcome id}", "fields": { "text": "<requirement text>", "type":
"<constraint|preference|ranking|task|other>" }, "creation action ids":
["<action id>"], "contributing action ids": [], "implementation action ids":
[], "related to": [], "explicit or implicit": "<explicit|implicit>", "rationale":
"<why extracted>" } ],
"open_slot ops": [ { "op": "open_slot", "slot id": "slot 1", "bound outcome id":
"{outcome id}", "fields": { "text": "<the hedged, uncertain, or deferred idea>",
"type": "<constraint|preference|ranking|task|other>" }, "origin": "<user|AI>",
"creation action ids": ["<action id>"], "contributing action ids": [],
"related to": [], "explicit or implicit": "<explicit = directly posed as an open
question/uncertainty; implicit = inferred ambiguity nobody named>", "rationale":
"<why substantive but failed Necessity>" } ] }
Use action ids (e.g. "U(3,1)" or "A(3,1)") in creation action ids / contributing
action ids / implementation action ids.

CRITICAL: Respond with ONLY the JSON object. No additional text.
```

### 6.2 Changes from the paper's original prompt

| Addition | Paper had | We changed to |
|---|---|---|
| `{actions block}` → `{outcome actions block}` | Same name reused ambiguously in Step 1b | Renamed to disambiguate (per-outcome FILTER, not whole dialogue) |
| PRIOR REQUIREMENTS section | No memory fed back in; the instruction "check for revise before create" had nothing to check against | New input section, enabling that instruction to function |
| PRIOR OPEN SLOTS section | Did not exist — no open-slot concept in the paper | New section, paired with the open_slot operation |
| Hedge/uncertainty/deferred-content paragraph | Necessity failures were simply dropped, regardless of reason | Redirects hedge-specific failures to a new operation instead of silent loss |
| `open_slot` operation (with resolve/abandon) | Only create/revise/delete existed | New 4th operation with its own sub-lifecycle |
| `open_slot ops` output array | Did not exist | New parallel output array, own id namespace |
| `(e.g. "U(3,1)" or "A(3,1)")` | `(e.g. "3-1")` | Updated to match Step 1a's id format |

### 6.3 The Necessity → Open-Slot decision path

```
Action raises something substantive
        │
        ▼
   Passes all 4 gates? ── YES ──► create (or revise/delete against prior requirements)
        │ NO
        ▼
   Failed Necessity due to hedge / uncertainty / deferred-content language?
        │ YES                                          │ NO (failed gate 2-4, or not
        ▼                                               │  substantive at all)
   open_slot  (M=0, tracked, origin=user|AI)             ▼
        │                                              dropped, no op emitted
        │  (on a LATER call, if firmly resolved)
        ▼
   resolve → becomes a real requirement (related_to → the slot it resolved)
        │  (if 3+ consecutive pairs pass with no resolution)
        ▼
   abandon → no longer carried forward
```

### 6.4 REQUEST

| Placeholder | Provenance | Exact source | Empty on first call for this outcome? |
|---|---|---|---|
| `{outcome id}` | **ECHO** | One `outcome_id`, from Step 1b. | No. |
| `{outcome description}` | **ECHO** | That outcome's `outcome` text. | No. |
| `{outcome actions block}` | **FILTER** | Full action objects where `action_to_outcome[id] == {outcome id}`. | No. |
| `{prior requirements block}` | **SELF-REFERENCE**, per-outcome | This outcome's own accumulated `requirement_ops`. | **Yes**, first call for this outcome. |
| `{prior open slots block}` | **SELF-REFERENCE**, per-outcome | This outcome's own accumulated `open_slot_ops`. | **Yes**, first call for this outcome. |

### 6.5 RESPONSE

## 7. STEP 3 — Influence Labeling

**Purpose:** for one requirement, determine which actions — before and after its creation —
actually influenced it, directly or indirectly. This is the mechanism behind Desideratum 2
(direct vs. indirect influence) and feeds the DIRECTION bar, the "AI's idea" lightbulb, and
the HOW-axis panel.
**Cadence:** per requirement, but **not simply once** — see §9 for the full two-trigger
iteration mechanism. Open slots never receive a Step-3 pass while still open; only once
`resolve`d into a requirement does processing begin.

### 7.1 PROMPT

```

Outcome: {outcome description}

=== TARGET REQUIREMENT ===
{req id}: {req text}

Origin: <directly created | resolved from open slot>

This requirement resolved from open_slot {slot id}, originally raised by
{user|AI} at {slot creation turn}: "{slot text}"

when this idea was first raised and tracked as an open slot. For each, assign

stronger or different label. Do not use NO CONNECTION for anything in this list.
{slot's creation + contributing actions, each as: action_id | action_type |

PROBLEM-TRIGGERED REVISION
Problem-Triggered-Correction | a prior failure, mismatch, or reported issue later

Complexity-Triggered-Simplification | prior complexity, burden, or ambiguity later

Extension-Driven-Next-Step | a prior invitation to continue later leads to a

Implementation-Triggered-Setup | a prior implementation request later leads to

TEMPORAL AND DIAGNOSTIC DYNAMICS
```

## 8. EVALUATION LAYER — Steps E1 & E2 (Requirement Satisfaction)

**Positioning — read this first.** These two prompts appear in the paper's appendix directly
after Step 3, but they are **not part of the core attribution pipeline** (Steps 1a–3 +
Stage 4 quantification). They are the paper's **evaluation suite**, used in its §4.2 to
compute **Requirement Satisfaction Rate** — the fraction of extracted requirements actually
met by the final artifact. We label them **E1/E2** (not "Step 4") to avoid collision with the
paper's Stage 4, which is Quantification. Two source-level caveats: the paper's validation
(Table 4) covers only Goal / Requirement / Influence Labeling — **no accuracy is reported for
either of these prompts**; and E1's input ("RELEVANT DIALOGUE TURNS") is **never defined
anywhere in the paper** — the same category of under-specification previously found and fixed
for `dialogue_summary` (§4.6). We define it explicitly below.

**Cadence — deliberately NOT per-pair.** A deliverable typically doesn't exist until late in
a conversation; re-extracting it every pair is pure waste, and E1 is the most token-expensive
prompt in the system (verbatim extraction of potentially large artifacts). Trigger: **session
end, or on demand**, per outcome. This layer's natural home in our design is the
report/summary layer, not the live rail.

**Architectural note — the return to RAW.** E1 is the first prompt since Step 1a whose input
returns to the **raw transcript** rather than extracted actions. This is forced, not
stylistic: a deliverable must be captured **verbatim**, and actions are third-person
paraphrases — no chain of prior outputs can reconstruct the artifact's literal text.

  introduced; this metric operationalizes that finding on our own data.
- **Silent resolutions** = count of `de facto resolved` slots — decisions materialized in the

values.

## 9. Full Pipeline Iteration Mechanism

This section explains, precisely, **when each step fires** across a growing, multi-pair
dialogue — the mechanism previously left implicit.

### 9.1 Level 1 — Steps 1a → 1b → 1c: strictly sequential, fixed cost

```
for each new pair P (in order, as the conversation happens):
    1a(P)                          → new actions, appended to STATE
    1b(all actions so far)         → full outcome tree re-emitted, action_to_outcome
    1c(outcomes so far)            → intentions re-emitted
```

Exactly **3 calls per pair**, always, no branching. For N pairs: exactly 3N calls. This tier
never fans out.

### 9.2 Level 2 — Step 2: bounded fan-out, only touched outcomes

```
for each new pair P (after 1a/1b/1c complete for P):
    touched = distinct outcomes that received a NEW action this pair
              (read from this pair's slice of action_to_outcome)
    for each outcome O in touched:
        2(O)   → requirement_ops, open_slot_ops for O
```

An outcome untouched this pair is **not** re-run — its requirements/slots stay exactly as
they were. Total calls across N pairs = Σ (outcomes touched per pair), bounded, but not
fixed like Level 1. A focused, single-outcome chat needs as few as N total Step-2 calls; a
chat that jumps between many outcomes needs more.

### 9.3 Level 3 — Step 3: two distinct triggers, not "one call per requirement"

This is the mechanism most easily mis-modeled as simpler than it is. **Section A is
permanent — bounded by a fixed origin turn, it never needs revisiting once computed. Section
B is open-ended — "after the origin turn" has no ceiling, so it keeps growing as long as the
outcome keeps receiving new actions.** This forces two separate triggers:

```
TRIGGER A — fires once, when Step 2 emits a "create" (or "resolve") op:
    new_req = the requirement just created/resolved
    origin_turn = earliest of new_req.creation_action_ids
    preceding = FILTER(all actions, whole dialogue, before origin_turn,
                        excluding creation_action_ids and any known-slot-origin ids)
    subsequent_so_far = FILTER(actions bound to same outcome, after origin_turn)
                         (often empty or small — the requirement was JUST created)
    3(new_req, preceding, subsequent_so_far, [slot origin if resolved])
       → full preceding_labels, whatever subsequent_labels exist so far

TRIGGER B — fires whenever an outcome gets a new action AND that outcome has
existing (non-deleted) requirements from EARLIER pairs:
    for each such existing requirement R:
        new_subsequent = FILTER(the newly bound actions only — not already labeled)
        3(R, preceding=EMPTY, new_subsequent)
           → subsequent_labels ONLY, appended to R's existing label history
        (Section A is never re-sent — it was already fully and permanently
         labeled at Trigger A)
```

**Consequence:** a single requirement can accumulate multiple Step-3 calls over the life of a
conversation — one initial (Trigger A) plus one incremental call (Trigger B) for every later
pair that adds new actions to its outcome. This makes Step 3 potentially **the most expensive
step in the whole pipeline by raw call count** — more than Step 2 — because Step 2's fan-out
is bounded per-pair, while Step 3's incremental re-runs accumulate per-requirement over the
outcome's entire remaining lifetime.

**Open slots are excluded from both triggers entirely** while unresolved — there is no `r` in
`I(a→r)` for an unresolved slot to be about. Processing begins only at the moment `resolve`
fires (which is itself a form of Trigger A).

### 9.4 The two-phase manual workflow (for a code-free, chat-based process)

Given Steps 1a/1b/1c/2 typically run inside one continuous chat (that chat already holding
all prior outputs in context), Step 3 is better split into two phases when working manually:

**Phase 1 — Assembly.** A single prompt, run in the chat that already holds Steps 1a/1b/2's
output, asking it to walk every outcome → every active requirement → determine Trigger A vs.
Trigger B applicability → assemble and format the correct input for each. Output: one clean,
labeled input block per requirement, ready to feed to Phase 2.

**Phase 2 — Labeling.** The Step 3 prompt itself (§7.1), run once per assembled input from
Phase 1.

### 9.5 Section-A candidate selection at build time (repo-informed recipe)

The manual workflow sends the full preceding action list. The official repo automates this
selection, and its parameters are known-good; adopt them when this pipeline is coded:
turn-level embeddings (`text-embedding-3-small`) of the requirement's origin turn vs. every
preceding turn; cosine ≥ **0.5** → candidate; candidates **restricted to turns sharing the
requirement's intention group** (Step 1c's output is load-bearing here — a fact absent from
the paper); the **adjacent previous turn is always included** regardless of score; turns of
`contributing_action_ids` are force-included. This closes most of §12.7's cost concern for
Section A. (Recipe not yet tested by us on our own data — flagged in §12.9.)

**Known limitation, not yet built:** the assembly prompt as currently specified always
assembles Section B in full, from scratch — it does not yet distinguish "give me everything"
(Trigger A) from "give me only what's new since the last pass" (Trigger B). Building that
distinction requires the assembly prompt to also track, per requirement, which subsequent
actions were already labeled in a prior Step-3 pass. This is a real, acknowledged gap — see
§12.6.

## 10. STAGE 4 — Quantification Layer (no prompt; pure computation)

**The defining fact:** unlike Steps 1a–3, Stage 4 has **no prompt and no model call**. The
paper's Stage 4 is three equations over the labels Step 3 already produced. Everything here
is code (or hand arithmetic), fully checkable, and §10.8 checks it against real data.

### 10.1 Inputs consumed

| Field | Born in | Used for |
|---|---|---|
| `turn id` prefix + pair index | Step 1a | Speaker split and pair bucketing of every score |
| `role` | Step 1a | Role-split (Eq. 3) and HOW signals |
| `creation action ids` / ops / `related to` | Step 2 | Automatic 5.0 scores, Decisions counter, resolve linkage |
| `open_slot ops` + `origin` | Step 2 [OURS] | Zero mass while open; slot-origin rows join at resolve |
| `relationship score` / `type` | Step 3 | The atom of every sum; IMPLEMENTS/REVISES/CONTRIBUTES feed HOW |

### 10.2 The paper's equations, plain words
- **Eq. 1** `I(a→r) = I_dir + I_ind` — already fully evaluated by Step 3: creation actions
  get the automatic 5.0 (*"actions in the origin turn receive maximal direct influence"* —
  applied by code, never LLM-judged); every other action's value is its Step-3 score.
- **Eq. 2** `M(p,r) = Σ_(a∈A_p) I(a→r)` — a party's mass on one requirement = the sum of
  that party's action scores on it.
- **Eq. 3** `M(p,ρ,r)` — the same sum filtered by role, `K = {SHAPER, EXECUTOR}` — **OTHER
  counts in Eq. 2's totals but is invisible to every role-split.**

### 10.3 The Influence Ledger [OURS]
The paper computes once over a finished dialogue; the live panel needs the same sums at
every pair. Mechanism: every score becomes one append-only row —
`(pair_added, action_id, speaker, role, outcome_id, req_id, score, kind)` where
`pair_added` = the pair whose pass PRODUCED the score (Trigger-B labels land in their own
time bucket) and `kind ∈ creation | labeled | slot-origin`. Rules: append-only, never
edited; one row per (action, requirement) score; open/abandoned slots add **no rows**
(slot-origin rows join only at `resolve`); NO CONNECTION adds no row. **Every panel number
is a query over this table.**

### 10.4 Increments and snapshots
`Δ(t,p) = Σ scores where pair_added = t, speaker = p` (the turn delta).
`C(t,p) = Σ_(t'≤t) Δ(t',p)` — stored per pair (the snapshot series; scrubbing = a lookup).

### 10.5 Panel derivations (each a one-line ledger query)
- **Direction @ t:** `you% = C(t,you)/(C(t,you)+C(t,AI))`.
- **Decisions:** creator = speaker of the EARLIEST creation action (mixed-creator
  tie-break); counts grouped by creator; latest AI example = highest-pair AI-created
  requirement's text.
- **Timeline:** collapsed delta bar = `Δ(t,·)`; drawer bars = per-turn per-requirement
  `Δ(t,p,r)` (per-turn scoping — locked in the panel spec; cumulative `M(p,r)` lives in
  level-2); chip color: blue if `M(AI,r)=0`, orange if `M(you,r)=0`, grey otherwise,
  evaluated as of the viewed pair.
- **HOW @ t:** signals `w_you/w_AI` (# requirements created, by creator), `h_you/h_AI`
  (non-creation mass added), `substantive_user` (any user SHAPER action, or any user
  non-creation row scoring ≥ 2). Classification (thresholds PROPOSED, unlocked until the
  two-trajectory calibration passes — Budget chat: Centaur E1–6 / Cyborg E7 / Centaur E8;
  Portfolio chat: Centaur → Cyborg E21 → Centaur E25):
  quiet pair (no ops, Δ total < 2) → inherit · `w_you ≥ w_AI and h_AI ≤ h_you` → CENTAUR ·
  `w_you ≥ w_AI and h_AI > h_you` → COPILOT · `w_AI > w_you and not substantive_user` →
  AUTOPILOT · `w_AI > w_you and substantive_user` → COPILOT.
- **Mode split:** % of non-quiet pairs per mode up to t.

### 10.6 Per-turn update loop
```
on pair t: 1a → 1b → 1c → 2 (touched outcomes; creation + slot-origin rows → LEDGER)
           → 3 Trigger A + Trigger B (labeled rows → LEDGER)
           → Δ(t,·); C(t,·) appended; counters, drawer data, HOW(t) queried
           → panel re-render at viewed pair
```
Cost per turn stays flat: queries are indexed lookups or one-pair filtered sums; growth
lives upstream (§12.2/§12.7).

### 10.7 Optional decay mode (repo-informed, default OFF)
The official repo's current math replaces flat sums with geometric chain decay for SHAPER
actions (`score × α^rel_distance`, α_direct = 0.8, α_indirect = 0.4, distance = rank along
the influential-turn chain from the requirement), normalizes non-SHAPER scores to /5, and
gives IMPLEMENTS a flat 1.0. Recency-weighting is defensible, but the scale becomes
heterogeneous (three currencies in one number) and it is neither the published math nor
documented outside code. **Not adopted.** Recorded here as a parameterized optional mode
for future experiments only; when OFF (default), Eq. 2 flat sums apply everywhere.

### 10.8 Worked proof (real data, verified by code)
Outcome 6 / req 1 (pair 1, Style-DNA chat): creation U(1,6)+U(1,7) = 10.0 you; labels
U(1,8)=2, A(1,37..41)=4,4,4,1,1 → `M(you)=12.0, M(AI)=14.0`, all SHAPER. Full pair-1 ledger
(157 rows, 14 requirements): `Δ(1,you)=87.0, Δ(1,AI)=314.0` → Direction **21.7% / 78.3%**;
Decisions **4 you · 10 AI**; HOW signals `w 4/10, h 47.0/239.0, substantive=true` →
**COPILOT**. Chain for every number: verbatim quote → action → requirement → score →
ledger row → sum → pixel.

## 11. Cross-Cutting Rules

### 11.1 Block size — B = 1 pair
Fixed at **B = 1 pair = 2 turns**, always. A simplification of the paper's default (B=4
turns) for live use.

### 11.2 Placeholder naming — deterministic, see §1.3
Permanent policy; no future placeholder may be reused across steps with different scope.

### 11.3 Determinism & tie-breaking
1. **Outcome vs. requirement, unsure?** → treat as a requirement, bias toward fewer nodes
   (mirrors the paper's own dominant error mode: 66.7% of goal errors).
2. **req_id / slot_id "collisions" across outcomes** → expected and safe *only if* every
   consumer reads `(outcome_id, req_id)` together, never the bare id. Verified mechanically.
3. **Hedge word present but sentence otherwise clearly mandatory** → still `create`.
4. **Slot unresolved for 3+ consecutive pairs** → `abandon`.
5. **JSON formatting inconsistency** → never trust literal whitespace. Parse with
   `json.loads()` immediately; re-serialize with `json.dumps(..., indent=2)`. Global rule
   after every call, not a per-prompt instruction.
6. **`dialogue_summary` stability** → keep unchanged unless purpose has materially shifted.
7. **Step 3 Section A vs. Section B asymmetry** → Section A is computed once, permanently, at
   Trigger A; never re-sent. Section B is open-ended and re-sent incrementally at Trigger B,
   containing only newly available actions since the last pass for that requirement.

### 11.4 Mechanical verification checklist (run after every real extraction)
- **Action coverage:** every Step 1a id appears exactly once in `action_to_outcome`.
- **Parent/child consistency:** if A lists B as a child, B's parent must be A.
- **req_id / slot_id isolation:** no action id cited in one outcome's requirements/slots
  belongs to a different outcome's bound action set.
- **req vs. slot disjointness:** no single action id justifies both a requirement and a slot
  within the same outcome.
- **Step 3 origin-action exclusion:** a requirement's own `creation_action_ids` never appear
  inside its own `{preceding block}` or `{subsequent block}` — they are pre-scored, not judged.

### 11.5 JSON output normalization (global, applies after every step's call)
Raw model output is parsed with `json.loads()` immediately, never displayed or stored raw.
The parsed object is the source of truth; formatting is regenerated by code, never trusted
from the model's literal text.

## 12. Known Risks & Open Questions (honesty ledger)

### 12.1 Open-slot accumulation
Mitigated by the 3-pair abandonment rule, not eliminated. Worth monitoring on long chats.

### 12.2 Accumulation cost — Steps 1b and 2
`{all actions block}` and each outcome's `{outcome actions block}` grow linearly with
conversation length. Deliberately deferred — build first, measure real cost, decide later.

### 12.3 Step 1b's missing prior-outcomes input
No explicit `{prior outcomes}` memory (unlike Step 2). Not yet resolved.

### 12.4 `confidence` field (Step 1b)
No rubric, never consumed downstream. **Recommendation: ignore.**

### 12.5 Deferred-commitment hedge test, unverified
The widened hedge/uncertainty/deferred-content clause (§6.1) has not yet been re-verified
against real data to confirm it closes the gap it was built to close.

### 12.6 Step 3's incremental (Trigger B) assembly is not yet built
The assembly prompt (§9.4, Phase 1) currently only supports full, from-scratch Section B
assembly. It does not yet distinguish Trigger A from Trigger B, meaning every re-run
currently re-sends and re-labels the full subsequent list rather than only new additions.
This is a real gap in the manual workflow, not yet closed.

### 12.7 Step 3 cost — now understood to be the pipeline's most expensive step
Per §9.3, a single requirement can accumulate many Step-3 calls over a long conversation's
life (one initial + one per later pair that extends its outcome). Not yet measured on real
data; deferred alongside §12.2 per the same build-first philosophy.

---

### 12.8 Evaluation layer (E1/E2) caveats
Three compounding cautions: (a) **no validation** — the paper's Table 4 reports accuracy for
Goal/Requirement/Influence extraction only; E1/E2 have no published accuracy at all;
(b) `{dialogue turns}` was **undefined in the paper** — our selection rule (§8.1.3) is our
own definition, reasonable but unvalidated; (c) E1 is the most token-expensive call in the
system (full verbatim artifact extraction) — another reason its cadence is session-end/
on-demand, never per-pair. The `is_reflected` binary is also deliberately coarse (no
partial-credit scale exists in the paper); treat satisfaction-rate numbers as indicative,
not precise.

### 12.9 v5 provenance and untested adoptions
The v0.2.0 taxonomy, rubric, and REVISES label are adopted from the official repo without
yet being re-verified on our own data (the pair-1 runs used the v3/v4 prompt — their
explanation fields use the old 6-item vocabulary; scores and structure are unaffected).
The §9.5 Step-2a recipe is documented from their code, not yet executed by us. The §10.7
decay mode is recorded but OFF. The §10.5 HOW thresholds remain uncalibrated. §12.5's
widened-hedge re-run is still the highest-value pending verification, since pair-1 panel
numbers sit on the un-re-verified requirement set.

## 13. Worked Example — One Action's Full Lineage

```
A(1,34)  "AI suggests Hybrid Pattern D... 'the likely path is Hybrid Pattern D'"

 1a │ role=SHAPER (proposing a direction)                         [CLASSIFIED]
    │ evidence_quote="the likely path is Hybrid Pattern D from the Bible"  [VERBATIM]
    ▼
 1b │ action_to_outcome["A(1,34)"] = "outcome 5"                  [STRUCTURAL JUDGMENT]
    ▼
 2  │ FILTER: A(1,34) included in outcome 5's {outcome actions block}  [mechanical]
    │ "likely" triggers the hedge redirect (§6.3)
    │ → NOT create → open_slot "slot 1", origin="AI"              [CLASSIFIED]
    │   creation_action_ids=["A(1,34)"]                           [STRUCTURAL JUDGMENT]
    ▼
    (future pair, IF the user commits to a specific tool path)
    │ → op="resolve" → NEW requirement created, related_to=["slot 1"]
    ▼
 3  │ Trigger A fires (new requirement created via resolve)
    │ Origin: resolved from open slot → KNOWN SLOT ORIGIN block built
    │ A(1,34) placed in KNOWN SLOT ORIGIN, NOT in Section A (excluded, §7.1)
    │ → IMPLICIT CONNECTION, score 3 (or higher if evidence supports it)
    │ preserving the full chain: AI-hedged-suggestion → tracked-as-slot →
    │ user-firmed-up → real-requirement → confirmed-influence-labeled,
    │ fully auditable end to end.
```

**Design target for every number the eventual panel displays:** traceable field-by-field,
through a chain exactly like this, all the way back to a verbatim quote in the original chat.
